**Результат.** `TextEditor.vue` **0% → 95.89% stmts / 85.18% branch / 92.85% funcs**, тесты **27/27, 0 todo** (было 0 исполняемых из 17). Агрегат по проекту 90.11 → **91.04 / 80.34 / 93.76 / 95.10** — branch впервые перешагнул 80%. Закрыты `texteditor.md` Issues 1 и 10.

**Почему это оказалось дёшево, хотя в assessment числилось эпиком C2 (4–7 д).** Рецепт был записан в roadmap с самого начала — `vi.mock("@vueup/vue-quill")`. Невыполнимым он был до Wave 2.1: пока Quill импортировался статически, подмена не успевала. После перевода на `await import()` в `onMounted` стаб перехватывает загрузку, и настоящий Quill не создаёт своих `requestAnimationFrame`-колбэков — тех самых, что стреляли после teardown jsdom и роняли прогон. То есть блокер сняла чужая волна, а roadmap об этом не узнал.

**Ошибка аудита, которую это вскрыло.** [closure-assessment.md](./closure-assessment.md) §3 поз. 11 утверждала: «0 `it.skip`, 15 живых тестов, `vi.mock` отсутствует — формулировка задачи устарела». Неверно: блок был под `describe.todo`, тестов ровно 17, как и говорил roadmap, а предложенный им `vi.mock` был правильным решением. Ошибка счёта возникла из-за того, что `describe.todo` не даёт `it.skip` в исходнике. Позиция снята из §3.

**Две технические детали, стоившие итераций:**

- фабрика `vi.mock` хойстится выше импортов файла — `defineComponent`/`h` приходится брать через `await import("vue")` внутри неё, иначе `ReferenceError: Cannot access '__vi_import_4__' before initialization`;
- нужны **два** `flushPromises()` подряд: в `onMounted` последовательно резолвятся `await import("@vueup/vue-quill")` и `Promise.all([...css])` — разные микротаск-очереди.

**Попутная находка N12.** Mount выдал `[Vue warn]: received a Component that was made a reactive object` — определение компонента лежало в глубоко-реактивном `ref`. Переведено на `shallowRef`.

**Находка N13 — кросс-файловая утечка, поймана pre-commit'ом.** Суита проходила при прямом запуске, но валилась на husky-хуке: `FixWindow.test.ts` падал с `TypeError: Cannot read properties of null (reading 'insertBefore')` плюс 23 unhandled-ошибки. Причина — `isolate: false` в [vite.config.ts](../../vite.config.ts): воркер переиспользует одно jsdom-окружение на несколько файлов. TextEditor тянет за собой InputLayout с mount-tick'ом на `setTimeout(100)`; тест завершается за ~5 мс, инстанс остаётся живым, таймер срабатывает уже во время следующего файла — когда документ подменён. Лечится `enableAutoUnmount(afterEach)`.

Практический вывод: **добавляя mount-тесты к компоненту, который раньше не монтировался, всегда ставь авто-unmount** — при `isolate: false` цена забытого инстанса ложится на чужой файл, и локальный прогон одного файла её не покажет. Стабильность подтверждена тремя полными прогонами подряд.

## T5 + T8. Label и `arrayHandler.sort`

**Батчи:** B2, B4.

| Подзадача | Что делаем |
| --------- | ---------- |
| T5.1 | Проверить, переваривает ли движок `var()` внутри arbitrary value |
| T5.2 | Заменить шесть px-литералов на три CSS custom property с fallback'ами |
| T5.3 | Обновить существующие тесты + завести тест на сам контракт переопределения |
| T8.1 | Установить фактическую семантику `sort` и задокументировать контракт стабильности |

**T5 — почему без токенов темы.** План в issue предписывал component-токены (`theme/Aurora.ts` → `$dt`) и был помечен «deferred to Wave 3.3». Wave 3.3 закрыта ещё 2026-07-02, то есть блокер снят. Но вариант с токенами добавил бы Label-специфичные ключи во все три пресета и в `ThemeSemantic` — расширение публичного API темы ради трёх чисел одного компонента. Взят более узкий путь: CSS custom properties с fallback'ами прямо в классах. Для потребителя результат тот же (`.my-form { --fv-label-translate-y: 68px }`), поверхность темы не растёт.

Ключевая проверка перед реализацией — движок должен уметь `var()` внутри arbitrary value **вместе с отрицанием и variant'ом**. Умеет:

```
-translate-y-[var(--fv-label-translate-y,60px)]
  → --fv-translate-y: calc(var(--fv-label-translate-y,60px) * -1)
```

Три переменные (`--fv-label-translate-y` 60px, `-offset` 48px, `-rest` 28px) покрывают все шесть `type`-вариантов. Fallback'и равны прежним литералам — визуально ничего не сдвинулось. Горизонтальные `translate-x-*` намеренно не тронуты: это Issue 9 (RTL), где нужна смена знака, а не параметризация.

**T8 — issue задавал вопрос, ответ оказался «вопрос некорректен».** `arrayHandler.sort` — не сортировщик, а **comparator**: принимает два значения, возвращает число, `Array.prototype.sort` внутри не вызывает. Стабильность обеспечивает вызывающая сторона и она гарантирована — `Array.prototype.sort` стабилен по спецификации с ES2019, библиотека evergreen-only. Дополнительно выяснено, что внутри `lib/` эта функция не используется ни одним компонентом (Table сортирует своим `localeCompare`-компаратором) — то есть это чисто публичная утилита.

Попутно закрыты ещё две позиции в `_utilities.md`: Issue 4 (coverage `dateHandler` **подтверждён** — те же 72.61 / 65.38, вопрос «требует подтверждения» снят, issue переквалифицирован в конкретный gap) и Issue 11 (`Utils.ts` — non-issue, заголовок не был зачёркнут и попадал в счётчики).

### Настоящий баг: `install()` мутировал встроенные пресеты и локали

Четыре новых файла проходили по отдельности и **падали в полной сюите** — признак утечки состояния. Причина оказалась не в тестах.

`install()` собирает конфиг как `deepMerge(defaults, userOptions)`, а `deepMerge` по канону библиотеки **мутирует первый аргумент** — это прямо записано в [utilities/objectHandler.md](../utilities/objectHandler.md) вместе с безопасным паттерном `deepMerge(deepCopy(defaults), overrides)`. Но `getDefaultOptions()` отдавал модульные синглтоны по ссылке. Замер:

```
Aurora.semantic  до    {"customThemeColor":0,...}
Aurora.semantic  после {"customThemeColor":210,...,"injected":"boom"}
Harmony.semantic после {"customThemeColor":210,...,"injected":"boom"}   ← протекло
en.save          до "Save"  после "MUTATED"
```

Harmony испортился потому, что все три пресета разделяют один `defaultSemantic` — находка предыдущего абзаца объясняет масштаб этой.

**Где это било по-настоящему — SSR:** один Node-процесс обслуживает много запросов, и конфиг первого становился дефолтом для всех следующих. Рядом — микрофронтенды (второе приложение наследует настройки первого) и `usePreset(Aurora)` поверх уже испорченного пресета.

Фикс — ровно тот паттерн, который библиотека сама документирует: `deepCopyObject()` на дефолтах. `deepCopyObject` уже был импортирован в файле, просто не применялся. Регрессия — [defaultsIsolation.test.ts](../../lib/config/defaultsIsolation.test.ts), 8 кейсов. Заведён как Issue 7 в [done/config.md](./done/config.md).

**Матрица:** `0/5/20/12` → **`0/3/18/12`**. Закрыты Theme Issues 2 и 3, Locale Issue 1, Nuxt Issue 7.

## T13. `dateHandler`: покрытие вскрыло мёртвый код и баг регистра

**Батч:** часть B10. Последний из трёх оставшихся `high`, который вообще можно было выполнить (два других — эпик и продуктовое решение).

**Результат:** `dateHandler.ts` **72.61 / 65.38 → 92.2 / 85.71**, порог 80 / 70 перекрыт. 37 новых кейсов в [dateHandlerMasks.test.ts](../../lib/utils/dateHandlerMasks.test.ts). Матрица Utilities `0/1/0/0` → `0/0/0/0`, файл перенесён в «Завершённые».

### Непокрытый блок был недостижим

Coverage годами указывал на строки 342–362 — switch по маскам внутри `formatDate`. Причина оказалась не в отсутствии тестов: **строкой выше стоит `mask = convertMask(mask)`**, которая переписывает маску до того, как switch её увидит. Все метки switch'а — исходные dayjs-маски, а на вход приходили уже конвертированные:

```
Do → do      W  → w      L    → P
WW → ww      WWW → EEE   ZZ   → xx
WWWW → EEEE  ZZZ → xxx   ZZZZ → zzzz
```

Ни одна не могла совпасть. Исполнить этот код было нельзя — метрика говорила правду, просто её читали как «не протестировано» вместо «недостижимо».

### Найденный баг

Единственной живой веткой была `case "a"`: и `A`, и `a` конвертируются в один токен. Поэтому `formatDate(date, "A")` возвращала **`"pm"` вместо `"PM"`** — хотя мёртвая ветка `case "A"` строкой выше объявляла верхний регистр.

Исправлено: регистр определяется по **исходной** маске, до конвертации. Обе ветки заданы явно — у date-fns токен `a` отдаёт верхний регистр, у dayjs нижний, так что и нижний приходится восстанавливать вручную. Это выяснилось на второй итерации: после первого фикса тест на маску `a` начал падать с `"PM"`.

### Почему мёртвый код удалён, а не «оживлён»

Соблазнительный вариант — перенести switch до `convertMask` и сделать его живым. Отвергнут: часть веток расходилась с семантикой dayjs, которую этот модуль эмулирует. `W` в dayjs — номер недели года, а switch отдавал `getDay()`, то есть день недели. `Do` — порядковый день месяца, а switch добавлял название месяца. То есть «оживление» сломало бы четыре маски ради починки одной.

Текущее поведение ближе к dayjs и теперь зафиксировано тестами по каждой маске. Заодно удалён ставший неиспользуемым импорт `getDay`.

Две вещи стоили итераций и полезны на будущее:

- **Размеры viewport'а надо подставлять на `HTMLElement.prototype` до `mount`.** jsdom не считает layout, а `measureViewport()` читает `clientHeight`/`clientWidth` уже в `onMounted` — подмена на элементе после монтирования не доезжает, окно остаётся нулевым, grid не считает колонки.

Добавлена нижняя граница. Хороший пример того, почему односторонняя граница в тесте — почти не тест.

### Отступление от буквы R13 — и почему оно верно по существу

R13 записано как «подключать **VirtualScroller** безусловно». Интегрирован не SFC, а его headless-ядро `useVirtualScroll`. Причина техническая: `VirtualScroller.vue` создаёт **собственный** скролл-viewport, и вложить его в `[data-select-list]` означало бы либо два вложенных скролла, либо перенос sticky-поля поиска и градиентных оверлеев в новую структуру — то есть переписывание разметки дропдауна ради переиспользования обёртки, тогда как нужное поведение целиком лежит в ядре.

Смысл решения при этом сохранён полностью: подключение безусловное, ветка одна, порог решает сам примитив, вторая реализация windowing не заводится. Показательно, что и сам [select.md Issue 7](./select.md) в пункте 1 плана предписывал именно composable.

### Что оказалось не так, как предполагал план

- **Prop `virtual?: boolean` не заведён.** План предлагал его (default `false`, backward compat), но по R19 порог внутренний, а по R13 ветка одна — prop'у неоткуда взяться. Инвариант закреплён тестом, который читает `Select.d.ts` и падает, если `virtual` или `virtualThreshold` там появится.
- **Виртуализация вскрыла отсутствие ARIA-ролей.** У списка не было ни `role="listbox"`, ни `role="option"` — при полном рендере это оставалось тихим долгом, но с окном превращается в регрессию: скринридер объявил бы «12 элементов» вместо 500. Роли и `aria-setsize`/`aria-posinset` добавлены не как улучшение сверх задачи, а как условие её корректности.
- **Fixed-size модель — сознательный предел.** Шаг строки 44 px выведен из `h-9` + схлопывающегося `mt-2`. Это делает кастомный `#item` нестандартной высоты несовместимым с окном; ограничение записано в Known issues, а не замаскировано `"auto"`-замером, который на списке в 10 000 позиций стоил бы дороже выигрыша.

### Находка N15 — `document.activeElement` глобален

Первый прогон уронил единственный тест: `ArrowDown ×2 + ArrowUp` вместо первой опции фокусировал третью. В изолированном воспроизведении всё работало.

Причина — в новой реализации «где сейчас фокус» определялось через `document.activeElement.closest("[data-select-list-item]")`. Прежний DOM-скан искал `indexOf` внутри **своего** `NodeList`, то есть был неявно ограничен собственным компонентом; `closest` такого ограничения не имеет и подхватил опцию чужого Select, оставшегося в документе от предыдущего теста. Индекс приезжал из чужого списка, шаг считался от него.

Лечится проверкой `ul.contains(el)`. Практический вывод шире теста: **любая замена локального DOM-поиска на глобальный (`document.activeElement`, `document.querySelector`) должна восстанавливать потерянную границу компонента явно** — на странице с двумя открытыми Select'ами баг воспроизвёлся бы и в проде, а не только при `isolate: false`.

## T16. Uno-движок: паритет с Tailwind v4

**Батчи:** [uno-engine.md](./uno-engine.md) Issues 2 (варианты) и 4 (утилиты), решение R15. Второй по порядку из-за R25.

| T16.2 | Варианты: `not-*`, `in-*`, `nth-*`, композиции `group-/peer- × aria-/data-`, container queries, `**:`, `starting:`, named `supports-*`, arbitrary at-rule |
| T16.3 | Important-модификатор в обеих формах (`!x` и `x!`) |
| T16.4 | Перенести реализованное из fail-closed-списков в позитивные тесты |
| T16.5 | Синхронизировать таблицу диалекта в `architecture/theme.md` и issue-файл |

**Результат.** Два новых тест-файла: [v4Utilities.test.ts](../../lib/theme/unoStyle/v4Utilities.test.ts) (52 кейса) и [v4Variants.test.ts](../../lib/theme/unoStyle/v4Variants.test.ts) (36). Полная сюита **5972 passed, 68 файлов**. Матрица `0/0/10/8` → **`0/0/8/8`**, строка Uno engine перенесена в «Завершённые».

### Что реализация вскрыла в самом движке

- **`skew-3` роняла движок.** Унифицированная форма v4 (без оси) попадала в `skew[undefined]`, которого в словаре не было, и вызов падал **до** всех fail-closed-проверок. То есть класс не дропался с warn, а бросал исключение. Найдено не тестом на баг, а попыткой реализовать форму.
- **`perspective-*` числилось «чужим семейством» по неверной причине.** В fail-closed-списке оно оказалось из-за того, что `perspective-origin-top` уводил разбор в правило `origin` (`transform-origin`) — то есть проблема была в порядке правил, а не в отсутствии реализации.
- **`@sm:` был не отказом, а ложным срабатыванием.** Символ `@` не участвовал в разборе, `sm` матчился обычным breakpoint'ом, и container-запрос превращался в viewport-`@media`. Такой класс «почти работает» на full-width контейнере и врёт на остальных — самый неприятный вид бага в движке стилей.

### Находка N16 — порядок альтернатив стал контрактом

Ветка `in-*:` перехватила `in-range:`: `in-` + `range` разбиралось как «предок в состоянии range», и рабочий псевдо-класс `:in-range` переставал генерироваться. Тест упал сразу — но сам класс проблемы шире одного случая.

Regex-alternation возвращает **первую** подошедшую ветку, а не самую длинную. После волны 3 это касается и вариантов (`not-`/`in-`/`nth-`/container раньше словарных, `**:` раньше `*:`), и словарей утилит (`light` перехватывал `light-dark`, `bottom` — `bottom-left`). Для словарей заведён хелпер `longestFirst()`, для `in-*` — защита, выводимая из самих словарей: список конфликтующих имён считается из них, а не хардкодится, поэтому новый псевдо-класс на `in-` не придётся вспоминать.

### Отступление от «полного паритета»: `mask-*`

R15 звучало как «добить до полной Tailwind v4 parity». Одно семейство осталось вне диалекта — и это осознанное решение, а не незакрытый остаток.

Статические части масок (`mask-clip-*`, `mask-size-*`, `mask-type-*`) — тривиальное отображение «класс → свойство». Но основная ценность семейства в v4 — маски-градиенты, а это подсистема из двух десятков связанных custom properties с композицией через `mask-composite` и собственными дефолтами в базовом слое. Воспроизводить её по памяти означало бы зашить правдоподобную, но непроверяемую модель: тесты подтверждали бы мою реконструкцию, а не поведение Tailwind.

Частичная поддержка была бы хуже обоих вариантов — граница диалекта перестала бы читаться одним правилом «`mask-*` не поддерживается». План самого Issue 4 относил `mask-*` к приоритету 3 «осознанно объявить вне диалекта»; это подтверждено, обоснование записано в [architecture/theme.md §3.1](../architecture/theme.md), поведение (fail-closed + dev-warn) не изменилось.

### «Три темы» были одной

Самая содержательная находка захода. Пресеты Aurora / Harmony / Sapphire делили один объект `defaultSemantic` с `customThemeColor: 0`, то есть брендовый слот у всех трёх был **серым**. Различались они полем `name` — и больше ничем. Тест от 2026-09-05 честно фиксировал это как «ожидаемое текущее состояние»; выяснилось, что состояние не ожидаемое, а просто незамеченное.

Обе половины исправлены разом: темы получили собственные оттенки (`25deg` / `152deg` / `217deg`), а поле `name` снято — оно не было объявлено в типе темы и проносилось через type assertion (это и был D21). Идентичность переехала в `config.optionsTheme.nameTheme`, где типизирована и, что важнее, **нормализуется**: опечатка в имени темы больше не остаётся в конфиге как «активная тема» при том, что фактически подставилась Aurora.

Тест теперь держит два инварианта вместо прежнего одного: «различаются ТОЛЬКО брендовым слотом» и «оттенки не повторяются» — второй не даст темам снова схлопнуться в одну.

### Semantic-слоты интентов — почему это не косметика

Alert красился примитивными шкалами (`bg-green-50`, `text-red-400`). Перекрасить «ошибку» в фирменный оттенок было нельзя, не переопределив всю палитру `red-*` — а её потребитель использует и в других местах. Четыре слота разводят интент и палитру: `updatePreset({ primitive: { error: … } })` меняет только Alert.

Механизм — тот же, что у структурного `surface` (Wave 9): это обычные именованные цвета движка. **Правок в движке не потребовалось** — цветовые regex собираются через `Object.keys(colors)`, новое имя подхватывается само. Дефолты равны прежним green / yellow / blue / red, поэтому визуально ничего не изменилось.

### Спиннеры: где хардкод действительно был виден

22 файла держали `#ff1d5e` в CSS и `#fff` в дефолте prop'а. На штатном пути это ничего не значило — `Loading` резолвит цвет из палитры и прокидывает инлайн-стилем, перебивая CSS. Но там, где инлайн-стиль не доезжает (SSR-снимок до гидратации; потребитель, импортирующий спиннер напрямую из `fishtvue/loading/epic/*`), показывался розовый или белый.

Перевод на `currentColor` закрывает оба случая. Заведён source-scan guard: 22 файла легко разъезжаются обратно, а глазами такой дрейф не ловится. Loading поднят до `stable` — Issue 7 был последним, что удерживало `beta`.

### Issue 7 темы (`primitive.ts` monolith) — wontfix с разбором

Закрыт не «по решению», а с проверкой предпосылки. План обещал tree-shaking неиспользуемых палитр — но движок собирает цветовые regex динамически, `Object.keys(colors)`. Объект нужен целиком в рантайме независимо от того, какие классы использует потребитель: имя цвета попадает в regex, а не в импорт. 22 файла всё равно импортировались бы все до одного.

Выигрыш при этом съедается сжатием — палитра однородна и хорошо жмётся. Показательно, что в тот же день файл вырос ещё на четыре слота: при per-color-разбиении каждый стоил бы отдельного файла и правки индекса.
